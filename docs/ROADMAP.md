## 2. 产品目标与边界

夜班台是 Windows 微信 PC 的本地拟稿助手。用户打开会话后，通过 `Ctrl+Alt+W` 或手工粘贴对话生成 2～3 条候选回复，最终由用户复制并在微信中发送。

当前边界：

- 只支持微信 Windows PC，不支持安卓、ADB 或手机自动化。
- 不做微信进程注入、内存读取、本地数据库解密或协议逆向。
- 金钱、帮忙承诺、情绪和工作决策属于高风险场景，只进入待确认队列。
- 当前产品不自动操作微信发送消息。
- 聊天原文、截图和反馈样本均保存在本机，并应受用户可见的隐私开关控制。

## 3. 当前架构

项目继续采用本地模块化单体结构，当前没有拆分服务或引入向量数据库的必要。

| 模块 | 路径 | 职责 |
|---|---|---|
| 桌面界面 | `wechat_draft_brain/ui/main_window.py` | 设置、手工拟稿、草稿队列、日志、托盘和隐私操作 |
| 编排层 | `wechat_draft_brain/pipeline.py` | 快捷键、配置刷新、OCR 去重、拟稿调用和结果持久化 |
| 大脑 | `wechat_draft_brain/brain.py` | 场景分类、安全策略、规则草稿和模型草稿 |
| 感知层 | `wechat_draft_brain/vision.py`、`chat_parser.py` | 前台窗口截图、OCR、气泡聚类和结构化会话解析 |
| 数据层 | `wechat_draft_brain/store.py` | SQLite 迁移、草稿、日志、状态和去重记录 |
| 配置 | `wechat_draft_brain/config.py`、`config/default.yaml` | 用户配置合并、校验、容错和隐私选项 |
| 打包 | `packaging/`、`scripts/build.ps1` | PyInstaller 目录版与 Inno Setup 安装包 |

关键架构决定：

- 保持 `brain.py` 只依赖文本和配置，不依赖微信窗口实现。
- 完整会话用于生成草稿，最后一条对方消息用于场景分类和安全判断。
- 当前继续使用 RapidOCR/ONNX Runtime；只有真实基线证明准确率或性能不达标时才评估替换 OCR 引擎。
- 个性化先使用 SQLite 精确条件和时间排序检索；样本规模和效果证明有需要后再评估向量检索。

## 5. 当前批次：P1-B 个性化反馈闭环

目标是先可靠记录“用户接受了什么、修改成了什么”，再让这些本地样本参与后续拟稿。当前批次不改变“用户最终发送”的产品边界。

### P1-B1 草稿反馈数据模型

状态：当前

计划提交：`feat(store): 增加草稿反馈数据模型`

实现范围：

- 通过下一版 SQLite 迁移增加候选序号、原始候选、最终复制文本、是否改写和反馈时间。
- 区分直接采纳、编辑后采纳和丢弃。
- 提供受控的数据层接口，避免界面任意拼接字段更新。

验收标准：

- 空数据库和版本 2 数据库均可无损升级。
- 直接采纳、编辑采纳和丢弃三种状态可以准确持久化。
- 历史草稿仍可读取，缺失的新字段使用安全默认值。

### P1-B2 编辑后复制交互

状态：计划

计划提交：`feat(feedback): 支持直接采纳与编辑后复制`

实现范围：

- 保留现有候选草稿的一键复制路径。
- 增加编辑后复制入口，保存原始候选与最终文本。
- 丢弃只记录负反馈，不进入正向个性化示例。
- 不读取微信输入框或剪贴板回写内容。

验收标准：

- 未修改直接复制时记录为直接采纳。
- 修改后复制时同时保留原始候选和最终文本，并记录为已编辑。
- 取消编辑不改变草稿状态；重复操作不会产生相互矛盾的反馈字段。

### P1-B3 本地样本管理与授权

状态：计划

计划提交：`feat(personalization): 增加本地样本管理与隐私开关`

实现范围：

- 增加“使用本地历史辅助生成”开关，默认关闭。
- 支持查看、删除、导入和导出本地反馈样本。
- 明确提示：启用模型个性化后，选中的历史示例会随请求发送到用户配置的模型接口。
- 聊天原文未保存、已清理或被丢弃的记录不作为正向样本。

验收标准：

- 个性化关闭时，模型请求内容与当前版本保持一致。
- 用户可以删除单条样本或清空全部样本。
- 导入数据经过格式、长度和字段校验；无效记录不会进入数据库。

### P1-B4 轻量 few-shot 拟稿

状态：计划

计划提交：`feat(brain): 使用本地反馈样本辅助模型拟稿`

实现范围：

- 优先选择同联系人、同场景的已采纳样本，其次选择同场景的最近样本。
- 每次最多加入 3 条示例，限制单条和总字符数。
- 检索逻辑放在数据层，提示词组装留在大脑层，通过明确参数连接，避免 `brain.py` 直接访问 SQLite。
- 规则拟稿不伪装成个性化结果；降级后仍显示真实生成来源。

验收标准：

- 没有样本、样本不足或个性化关闭时均能正常生成草稿。
- 检索顺序、数量上限和字符上限有自动化测试。
- 提示词不包含 API Key、事件日志或未授权历史记录。

### P1-B5 真实样本评估

状态：计划

所需输入：约 20～30 组脱敏后的“对方说了什么 → 用户最终怎么回复”，覆盖家人、同事、普通好友和需要谨慎回应的人。

验收标准：

- 固定同一批输入，对比未启用和启用个性化后的候选草稿。
- 记录可直接使用率、需要改写率、语气偏差和不应模仿内容。
- 只有真实对比结果支持时，才把“个性化效果提升”写入已完成能力。

### 暂缓事项

- 自动操作微信发送消息：不在当前路线中，需要用户重新确认产品边界和风险后才能立项。
- 向量数据库：当前样本规模不需要；先验证 SQLite 轻量检索的效果。
- 替换 OCR 开源项目：当前没有足够基线证明必须迁移，先继续收集真实识别失败样本。
- 微服务拆分：本地单用户桌面程序暂时没有服务拆分收益。

## 7. 通用完成标准

每个开发项只有同时满足以下条件才能标记为已完成：

1. 实现范围内的代码和数据迁移已经完成。
2. 正常路径、异常路径和关键边界具有自动化测试。
3. 相关测试通过，必要时完成目录版构建和隔离用户目录启动验证。
4. 暂存区经过审计，没有混入探索脚本、真实截图、数据库或其他无关文件。
5. 一个独立问题对应一个符合仓库规范的 Git 提交。
6. 本路线图补充实际提交号、验证结果和仍未覆盖的限制。

## 8. 已知限制与发布前检查

- OCR 依赖窗口布局、缩放比例、主题和图片质量，仍需持续用脱敏真实截图回归。
- 当前只通过截图理解会话，无法知道用户最终是否真的在微信中发送了复制内容。
- 用户在微信输入框中二次修改的内容不会被读取，也不会成为反馈样本。
- 未配置 API Key 时使用规则草稿，个性化 few-shot 只能在模型生成路径生效。
- API Key 当前仍保存在本机用户 YAML 中，尚未使用 Windows 凭据加密。
- 安装包未签名，Windows SmartScreen 可能显示提醒。
- 发布前仍需在真实微信前台窗口完成快捷键、OCR、草稿复制和隐私清理的人工端到端验收。
